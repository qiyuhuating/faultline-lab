# Explain it, then extend it

## 六个必须讲清楚的问题

**为什么用租约，而不是 running=true？** 进程可能死亡，布尔状态无法区分“正在执行”与“永远没人执行”。租约提供有限的所有权时间，过期后允许恢复。

**为什么租约之外还需要 token？** 过期 Worker 可能只是卡顿，并没有死亡。它恢复后不能覆盖新的执行结果；owner + token + deadline 检查将旧提交拒绝。

**为什么幂等键不能只检查是否出现过？** 同键不同内容必须冲突。否则用户把原请求键用于新意图，会得到看似成功但内容错误的结果。

**为什么不能承诺所有任务 exactly-once？** Worker 可能完成外部副作用但在记录成功前崩溃。本地事务只能保证自己的数据库写入；远程系统需要自己的幂等协议。

**SQLite 会不会阻止多个进程？** 它允许多个进程访问同一文件，但写事务由单写者串行化。这个设计用它协调本机领取；它并没有提供跨机器共享文件可靠性或无限写吞吐。

**事件链为什么不是安全审计？** 能修改数据库的人也能改锚点和重新计算 hash。当前链用于一致性检查，缺少独立可信签名与外部锚定。

## 三个能够产生你自己贡献的练习

1. **加入一个新纯计算处理器**：如 JSON 数组去重。先定义输入范围、验证失败语义，再补处理器、API 类型、界面选项及真正的错误测试。保持结果在当前 fenced 事务里提交。
2. **把租约参数安全配置化**：允许 CLI 配置 leaseMs 和 heartbeatMs，验证心跳间隔应明显小于租约。补过短值拒绝与真实慢任务续约测试。
3. **改进过载可观察性**：测量 claim 等待和 SQLite busy 次数；用真实数据定位瓶颈。基准测试的 workload 与硬件保持一致，再比较修改前后。

## 建议的学习顺序

先看 schema.sql、domain/types.ts 和 validation.ts，再从 queue.ts 定位 JobService、LeaseService 与 SqliteStore。沿 submit → claim → complete/expire 追踪事务，再阅读 worker.ts 与 server.ts 的进程退出流程。最后对照测试逐条运行故障实验。

不要背诵术语来替代实验：暂停队列再提交；同时打开两个页面处置；观察故障进程 PID；导出并修改一条事件后运行验证工具。把结果及自己的修复记录写到独立笔记。

## v1.0.1：四个可以现场追问的故障

- **为什么续租前取时间仍然可能错？** 等待数据库锁本身会消耗时间。开始等待时合法，不代表拿到锁后仍合法；应在取得写锁后再判断 deadline。
- **计算成功、保存失败，为什么不能直接 fail？** 它把基础设施错误伪装成业务处理错误。当前选择保留租约，由到期恢复，且总尝试预算仍有限；外部副作用需要自己的去重协议。
- **有 revision 为什么条件刷新还会漏变化？** revision 是事件序号，离线判定、时间窗和保留策略不一定追加事件。条件读取需要覆盖实际展示内容。
- **为什么 close 必须等到结束才算完成？** 调用方可能随即删除目录或重启服务。提前返回会让它与仍运行的 HTTP 请求、Worker 和数据库争抢资源。

运行 tests/resilience.test.mjs，亲眼观察真实锁等待和 SQLITE_FULL；阅读 batch-05 的修复前记录，再解释每条修复如何改变行为。

## v1.1.0：类型与拆分追问

1. 如果 succeeded 的结果允许 null，哪条负向编译测试会失败？为什么类型擦除不会阻止它？
2. 为何 LeaseService 不自己开第二个数据库连接？审计追加失败后哪些表必须回滚？
3. SQL 查询的泛型返回类型是否等价于运行时验证？如何测试数据库里 owner 丢失的 running 记录？
4. 试着从 storage 导入一个服务，或在 Queue 加入 SQL。哪道验收应该拒绝？
5. 取消、重放、租约 token、revision 与 generation 分别解决什么问题？哪些判别联合能防止错误，哪些仍须数据库原子性保证？
